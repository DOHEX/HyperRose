## 1. 结论

琉璃 Ultra 走 **Bluetooth Classic RFCOMM**(非 BLE GATT)。控制通道 RFCOMM 通道 6,自定义服务 UUID
`0cf12d31-fac3-4553-bd80-d6832e7b3931`,与仓库 `BudsFeelMk2Profile.dataChannelUuid`
**逐字节相同**。帧格式、校验和、ACK、`0x1E` 状态查询、`0x09` 降噪模式、`0x0E` 游戏模式与共享的
`RoseRfcommCommandSet` / `RoseRfcommProtocol`(app/src/main/kotlin/com/dohex/hyperrose/profile/rfcomm/)
完全一致 → 琉璃 Ultra 属于同一 ROSE RFCOMM 协议族,可直接复用现有协议适配层。

抓包额外确认了仓库尚未覆盖的内容:

1. 7 个新命令:`0x2C` 降噪深度、`0x2D` 通透深度、`0x2A` EQ、`0x45` 增益、`0x2F` 查找设备、
   `0x07` 提示音语言、`0x2E` 提示音等级,以及触控配置 `0x01`。
2. 降噪模式新增两个值:`0x05` 自适应降噪、`0x06` 极限降噪(仓库只支持 01-04)。
3. 全量状态帧多了一段 20 字节的"触控对"区段,现有 `RoseRfcommResponseParser.parseTlvBlock`
   在该帧上**脱同步**(已用抓包 payload 模拟验证,只碰巧命中 09/0E 且值错误,漏掉全部有效 TLV)。
4. 耳机存在主动电量推送帧(len=0x04,cmd 0x0C),现有 `parse()` 顶层分派会落 `Unknown`。

## 3. 帧格式

```
手机→耳机: FF <seq> <len> <cmd> <payload...> <CK> <AA>
耳机→手机: DD <seq> <len> <cmd> <payload...> <CK> <AA>
```

- `seq`:发送侧独立递增计数器(手机 00..3A,耳机 00..4D,互不相关)。
- `len` = 1 + payload 字节数(即 cmd + 参数)。**例外:全量状态帧 len=0x15 只覆盖段 A,见 §6。**
- `CK` = 帧头至 payload 末尾所有字节求和 `& 0xFF`。
- `AA` 帧尾。
- 校验和已在全部帧上验证通过(含 73 字节状态帧,证明其为单帧而非重组拼接)。

示例:

```
FF 03 02 2C 05 35 AA     # seq=03, len=2, cmd=0x2C(降噪深度), 值=0x05(深度), CK=0x35
DD 00 02 FE 00 DD AA     # ACK
```

## 4. 命令表(手机→耳机)

以下"对应操作"来自本地操作记录 `.local/research/ceramics-u/notes/operation-order.md`,与抓包时间线 1:1 对齐。

| 功能 | cmd | 值 | 对应操作 | 备注 |
|---|---|---|---|---|
| 查询全部状态 | 0x1E | `FA 01` + 28 个状态键 | 连接后同步×3 | payload 与仓库 `QUERY_PAYLOAD` 逐字节一致 |
| 降噪模式 | 0x09 | 01=降噪, 02=普通, 03=通透, 04=风噪, **05=自适应降噪, 06=极限降噪** | 风噪→04, 降噪→01, 普通→02, 通透→03;末尾 自适应→05, 极限→06, 极限关→02 | 01-04 仓库已支持;05/06 新增。模式变更后有回显 |
| 降噪深度 | 0x2C | 01=轻度, 03=中度, 05=深度 | 深度降噪→05, 中度→03, 轻度→01 | 值为奇数档(1/3/5),可能还有 2/4 档未抓到 |
| 通透深度 | 0x2D | 01=标准, 05=深度 | 深度通透→05;之后另有 01(标准重选) | 初始状态 2D=01 |
| EQ 预设 | 0x2A | 00=HIFI, 01=POP, 02=ROCK, 03=经典 | 经典→03, POP→01, HIFI→00, ROCK→02 | 按点击顺序映射;初始状态 2A=02(ROCK) |
| 增益 | 0x45 | 00=增益1, 01=增益2, 02=增益3 | 增益3→02(双写), 增益1→00, 增益2→01, 增益1→00 | 值 = 档位 − 1;增益3 有 ~350ms 双写(App 行为) |
| 游戏模式 | 0x0E | 01=开, 00=关 | 游戏模式开/关 | 仓库已支持;有回显 |
| 查找设备 | 0x2F | 01=左耳, 02=右耳, 04=停止 | 左开→01, 左关→04, 右开→02, 右关→04(+1 次重复 04) | 停止(04)后耳机回显 `2F:06` + `2F:05` |
| 触控配置 | 0x01 | `<键> <动作值>` | 8 组手势,每组写 2 次(改后还原) | 键 01-05=左耳, 11-15=右耳;动作值 00/01/02/03/04/05/07/08 |
| 提示音语言 | 0x07 | 01=英文, 00=中文 | 英文→01, 中文→00 | 初始状态 07=00(中文) |
| 提示音等级 | 0x2E | 05..01 = 5级..1级 | 5级(双写), 4/3/2/1 各一次 | 初始状态 2E=01(1级) |
| 未知开关 | 0x31 | 01/00(净零,两次写回) | 文档未列 | 初始状态 31=00 |
| 未知子配置 | 0x36 | `36 01 01 <00\|01>` | 文档未列(极限降噪关之后) | 状态值 `01 00 00 01` |

**0x45 vs 0x2F 归属判定**:若 45 为查找设备,则字节序列 `02,02,00,01,00` 中"左关=02=左开"矛盾;
而 45 对应 增益3/1/2/1 完全吻合 → **0x45 = 增益,0x2F = 查找设备**。

**已知 App 层行为(非协议)**:
- 增益3、提示音5级:同一值 ~350ms 内双写。
- 触控配置:8 组手势各写 2 次,前后值不同(初始状态 → 改 → 还原),净变化为零。
- 0x31:两次写回(01 后 00),净变化为零。

## 5. 耳机→手机帧

| 形态 | 字节 | 说明 |
|---|---|---|
| ACK | `DD <seq> 02 FE 00 <CK> AA` | 每条命令后必回,值恒为 00 |
| 状态回显 | `DD <seq> 02 <cmd> <val> <CK> AA` | `0x09` 模式(05 会回显两次)、`0x0E` 游戏模式、`0x2F`(仅对 04 回显 `06`+`05`,疑为左右耳停止确认) |
| 电量推送 | `DD <seq> 04 0C <L%> <R%> <盒%> <CK> AA` | 例:`DD 0D 04 0C 64 63 35 F6 AA`(L=100, R=99, 盒=53) |
| 全量状态 | `DD <seq> 15 ... <CK> AA` | 见 §6;共 73 字节 payload |

回显时序(以 0x09 为例):

```
19.135 P→B  FF 06 02 09 04 14 AA     # 设置风噪
19.180 B→P  DD 09 02 FE 00 E8 AA     # ACK
19.573 B→P  DD 0A 02 09 04 F6 AA     # 回显当前模式
```

## 6. 全量状态帧(关键差异)

```
DD <seq> 15 <段A: 21字节> <段B: 52字节> <CK> AA
```

- **len 字节 0x15=21 只覆盖段 A**;段 B 延伸至帧尾。校验和覆盖全部 73 字节(已验证)。
- 三份状态转储(seq 01/03/05,对应三次 0x1E 查询)内容逐字节一致,仅 seq/校验和不同——
  耳机不主动重推全量状态,仅回显变更。

### 段 A(21B):触控配置状态

`cmd 01` + 10 组 `(键,值)` 对:

| 键 | 值 | | 键 | 值 |
|---|---|---|---|---|
| 01(左单击?) | 03 | | 11(右单击?) | 05 |
| 02(左双击?) | 01 | | 12(右双击?) | 01 |
| 03(左三击?) | 08 | | 13(右三击?) | 08 |
| 04(左长按?) | 02 | | 14(右长按?) | 03 |
| 05(左,未配置) | 00 | | 15(右,未配置) | 00 |

键空间与触控命令 `0x01 <键> <动作值>` 一致(命令只出现 01-04/11-14,05/15 从未被写)。

### 段 B(52B):设置 TLV

TLV 格式 `<len> <key> <value...>`,`len` = key + 值字节数。共 15 项:

| key | 值 | 含义 |
|---|---|---|
| 07 | 00 | 提示音语言(00=中文, 01=英文) |
| 09 | 01 | 降噪模式(01=降噪;见 §4) |
| 0C | 64 64 35 | 电量 L/R/盒(100/100/53) |
| 0D | 00 03 04 | 未知(3 字节) |
| 0E | 00 | 游戏模式(00=关, 01=开) |
| 12 | 01 | 未知 |
| 2A | 02 | EQ 预设(02=ROCK) |
| 2B | 00 | 未知 |
| 2C | 01 | 降噪深度(01=轻度) |
| 2D | 01 | 通透深度(01=标准) |
| 2E | 01 | 提示音等级(01=1级) |
| 31 | 00 | 未知开关 |
| 32 | 01 | 未知 |
| 33 | 00 | 未知 |
| 36 | 01 00 00 01 | 未知子配置(4 字节) |

初始状态还原:模式=降噪、深度=轻度、EQ=ROCK、提示音=1级、语言=中文、游戏=关。
注:查询 payload 包含 28 个键(07 08 09 0C 0D 0E 12 2A 2B 2C 2D 2E 2F 31 32 33 36 37 38 39 3A 3B 3C 3D 3F 45 46 49),
但状态帧只回 15 个;`2F/45`(查找/增益)等为瞬态/无持久状态,不在全量状态中。

### 与仓库解析器的差异

仓库 `RoseRfcommResponseParser`:

- 按 `data[2]`(len 字节)分派:0x15=状态,0x02=短通知,其余(含电量推送 len=0x04)→ `Unknown`。
- `parseTlvBlock` 从第 4 字节直接按 TLV 解析,**在段 A(触控对)上脱同步**。用抓包 payload 模拟后
  仅"碰巧"命中 09/0E 各一次且值错误,漏掉 0C 电量、2A EQ、2C/2D 深度、2E 提示音等全部有效 TLV。

修复方向:状态帧先识别/跳过段 A(cmd 01 + 20 字节),再从段 B 起按 TLV 解析;并补充 len=0x04
电量推送(0C + L/R/盒 3 字节)的分派。

## 8. 未知项(需 UI 对照或二次抓包)

1. `0x2F` 回显 `06/05` 的确切语义(推测:左右耳查找停止确认)。
2. `0x31`(01/00 净零)、`0x36`(`01 01 <v>` 子配置)的功能。
3. 状态 TLV `0D/12/2B/32/33` 键含义。
4. EQ 值→预设名的精确对应(按点击顺序推断 00=HIFI/01=POP/02=ROCK/03=经典;初始 2A=02 与"默认 ROCK"
   略反常,建议用单设备对照抓包复核)。
5. 触控动作值(00-08)与动作(音量/上一首/语音助手…)的映射。
6. `0x2C` 是否还有 2/4 档(本次只出现 1/3/5)。
